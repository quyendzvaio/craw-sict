# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Multi-modal RAG crawler for `https://sict.haui.edu.vn/vn`: crawls the site tree → text, tables, images, video keyframes → PostgreSQL + Qdrant + S3, then serves a RAG Q&A API + chat UI. Code comments, docs and commit-facing text are mostly Vietnamese; keep that convention.

## Commands

Dependencies are managed **only with uv** (`pyproject.toml` + `uv.lock`). Do not use pip or add `requirements.txt`. Dependency groups: `dev` (pytest), `api` (FastAPI/uvicorn), `ml` (torch CPU, sentence-transformers, transformers, pytesseract, yt-dlp, playwright as a CDP client only — never run `playwright install`).

```bash
docker compose up -d postgres redis qdrant      # local infra
uv sync --group dev --group api                  # add --group ml for embedding/OCR/video
uv run uvicorn sict_crawler.api.routes:app --port 8000  # API + chat UI at /
```

Tests (same as CI, `.github/workflows/ci.yml`):

```bash
uv run pytest tests/ -q --ignore=tests/smoke_incremental.py
uv run pytest tests/test_safety.py::test_mass_delete_guard   # single test
uv run python -m tests.test_safety     # these 3 also run as scripts in CI
uv run python -m tests.test_captions
uv run python -m tests.test_agent
```

`smoke_incremental.py` needs live services (PG + Qdrant `*_v2` loaded by `loader`, run inside the worker image with `--artifacts A`) and is excluded from CI; it writes to whatever DB it points at, so use it on dev only. `test_behavior_contract.py` / `test_retrieval_response_contract.py` are spec tests written from `tests/acceptance_criteria.md` and `tests/acceptance_retrieval_response.md` (IDs like `AC-B1`, `AC-E4`, Gherkin in `tests/features/`); they encode the intended policy with stdlib `unittest` and don't import the real code yet.

Pipeline CLI (`sict_crawler/pipeline/main.py`), one mode per invocation:


```bash

python -m sict_crawler.pipeline.snapshot --out _snapshot/2026-10-12 --export-only
python -m sict_crawler.pipeline.compute --snapshot _snapshot/2026-10-12      # stages docs,text,images,videos

python -m sict_crawler.pipeline.loader --artifacts _snapshot/2026-10-12/artifacts/v2-multilingual-e5-small [--recreate]

python -m sict_crawler.service.graph.graphsync rebuild | stats | review-export f.csv | review-import f.csv
python -m sict_crawler.service.graph.graphsync block event "học máy"               # reviewed block / alias = data
python scripts/eval_graph.py --gold eval/graph_gold_v1.jsonl --pred rules|llm|<file> [--ref llm] [--errors N]
```

## Code layout

`sict_crawler/` is split by responsibility; imports are absolute (`from sict_crawler.repository import vector_store`) and only point down this list (a layer never imports one above it; `api` and `pipeline` are both top layers and do not import each other):

| Package | Holds |
|---|---|
| `core/` | `config` (yaml + env → dataclasses), `text.fold` (accent folding), `sparse` (BM25 tokens). No project imports. |
| `model/` | `orm` (SQLAlchemy tables), `schemas` (pydantic `QueryIn`, `Source`). |
| `repository/` | Storage access: `db` (PG session, `init_db` ALTERs), `vector_store` (Qdrant), `storage` (S3 / local store), `frontier` (Redis crawl queue), `cache` (Redis db 3 best-effort cache). |
| `service/crawl/` | `crawler` (+ `crawler_obscura`), `parser` (HTML → markdown + blocks), `urls` (page type, pagination depth, YouTube id, error page). |
| `service/index/` | `indexing` (spec v2 rules: metadata, cleaning, chunks, attachments), `doc_rules` (page/attachment doc, chunk rows, caption text, uuid5 `stable_id`: shared by bulk compute and incremental), `indexer` (the v2 write path), `chunker`, `ocr`, `video`, `annotate_ocr` (v1). |
| `service/embedding/` | `embedder` (client gateway: torch or HTTP API), `embed_server` (self-hosted ONNX service; its image copies only this file, so it imports nothing from the project). |
| `service/retrieval/` | `retriever.retrieve` (hybrid search, media, use cases U1–U7, query cache key), `sources` (hit → `Source`, numbered LLM context), `agent` (one retrieval pass + rule-based `evidence`, D27), `query_rewriter`, `router`, `filters`, `citations`, `vlm` (LLM calls). |
| `service/graph/` | `graph` (rules, gazetteer), `graphsync` (the only build path), `graph_catalog.yaml`. |
| `pipeline/` | Jobs / CLIs: `main` (crawl CLI, `--incremental`), `incremental`, `discover`, `snapshot`, `compute`, `loader`, `reconcile`. |
| `api/` | HTTP only: `routes` (FastAPI app, `uvicorn sict_crawler.api.routes:app`), `metrics` (`GET /metrics`), `ui/`. |

Tests live in the top-level `tests/` (fixtures, Gherkin `features/`, acceptance criteria `.md`). Bare module names in the sections below (`indexer`, `retriever`…) refer to this table.

## Architecture

**Ingest pipeline** — `frontier` (Redis BFS queue `frontier:list`, `frontier:seen` dedup, per-host politeness) → `crawler.fetch` → `parser` (markdown, tables, image/video URLs) → `chunker` (token budget, optional semantic splitting via E5) → `embedder` (E5 multilingual-small 384-d for text, CLIP ViT-B/32 512-d for images) → `vector_store` (Qdrant `sict_text`, `sict_image`) + `db`/`models` (PG: `documents`, `chunks`, `media_assets`) + `storage` (S3).

- `main._process_page` is the core per-page unit and delegates to `indexer.index_page` (index spec v2, same rules and uuid5 ids as bulk compute). It is idempotent: `documents.hash_v2` (sha1 of the cleaned markdown, not raw HTML, whose view counter changes on every fetch) unchanged → skip; changed → set `hash_v2=NULL` and commit, remove the doc's points, then rewrite. Listing pages are not indexed but their links are pushed (pagination keeps depth). `incremental.py` reuses it. `--rechunk`, `--videos-backfill` and `--annotate-ocr` are v1-only and refuse to run against a v2 collection.
- `crawler.fetch` backend via `CRAWLER_BACKEND` (`auto|httpx|obscura|crawl4ai`). `auto` = httpx first, Obscura CLI (`crawler_obscura.py`) if the HTML looks like a JS shell, crawl4ai last.
- **Images**: stored S3-only (`base64_data` in PG is now `""`; older rows may still have base64, so readers check base64 first then S3). Alt text becomes the initial caption.
- **Video** (`video.py`): ffmpeg scene keyframes (max 20, CLIP-deduped) stored as `kind=video_frame` and retrieved like images. Transcript is **subtitle-only** via yt-dlp (no ASR/Whisper). Never store full videos. YouTube cookies come from `$YT_COOKIES` (mounted `./cookies/`, rotated via `.github/workflows/cookies.yml`; never commit cookies).
- **Captions** (`annotate_ocr.py`): caption = doc title + Tesseract OCR text, embedded with E5 into `sict_text` as `kind=media_caption`. Video frames of the same video share one aggregated caption point. Face recognition and VLM captioning were removed (`vlm.enabled: false`); `vlm.py` is still used for LLM answer streaming and query rewriting.
- **Incremental** (`incremental.py`): discover new URLs from seeds → **refresh every listing section** (`refresh_listings`: seeds + sections derived from article URLs in PG + listing URLs in `frontier:seen`, fetched directly every run because `frontier:seen` never expires; page 2, 3… only while the page still has unknown posts of that section, capped by `crawl.listing_max_pages`) → recheck the N oldest non-attachment docs → drain frontier. Drain records transient failures (timeout, 5xx, empty body, processing error) in `frontier:fails` / `frontier:retry` and re-queues them at the start of the next drain, up to `crawl.max_fetch_retries`; 404/410 is final. OCR now runs inline while indexing (`media.ocr_status`); the separate OCR stage only runs against v1 collections. Safety rules: only HTTP 404/410 delete a doc (`should_delete`, via `indexer.remove_document`: Postgres delete + commit first, then Qdrant, so a failure leaves orphan points rather than a doc without points), and a mass-delete guard aborts the pass past an absolute/relative threshold (`mass_delete_abort` → `MassDeleteAbort`; before 2026-10-14 the per-doc `except` swallowed it). Stages are isolated; heartbeat written to Redis `incremental:last_ok` / `incremental:last_error`. Qdrant writes go through `_with_retry`; `ensure_payload_indexes()` creates `document_id` integer indexes (deletes are slow without them).

**Bulk index path** (snapshot → compute → `loader`; config defaults to the `*_v2` collections):
- `snapshot.py` downloads only: HTML (gz), content-region images, attachment files, and a video list into `_snapshot/<date>/`, with state in `state.sqlite`. It crawls only the SICT host. Pagination links keep the parent depth, because the site only links to the next page and depth-limited BFS would otherwise stop after about 5 listing pages per section. `state.sqlite` runs in WAL mode so read-only inspection does not lock the crawler. Open it with `?mode=ro`. `frontier.canonicalize` forces https and strips the trailing slash, because the site mixes both and pages were otherwise fetched twice.
- `indexing.py` is index spec v2 and the single rule set for both bulk compute and (to be switched) incremental. It covers metadata (`section`, `doc_type`, `published_at`, `year`), markdown cleaning, context-header chunks, table chunks that repeat the header row (a table whose normal split yields a piece over 2×`max_tokens` — layout tables built from merged cells, e.g. one 2019 page with a 389-column row — is re-split compactly: empty cells and `---` rows dropped, a header longer than `max_tokens/4` not repeated, long rows split by cell groups; every other table stays byte-identical, so applying it on 2026-10-21 changed one document only: 80 → 10 chunks), a boilerplate hash, and attachment text (`pdftotext` and stdlib zip-XML; no extra deps).
- Attachments: the site serves files with wrong extensions (xlsx named `.xls`, docx named `.doc`), so `indexing.sniff_format` decides by magic bytes. Legacy OLE2 doc/xls go through `catdoc`/`xls2csv` (apt `catdoc`, in the worker image). Scanned PDFs are OCRed page by page with `OMP_THREAD_LIMIT=1` when `ocr_scanned=True`, which compute sets. The snapshot gives up on a host after 5 consecutive connection errors (dead legacy domains). For long snapshot runs, use the Docker container `sict-snapshot` (`--restart unless-stopped`, idles after finishing): the dev box reboots and kills plain background processes.
- `compute.py` turns a snapshot into store-agnostic artifacts (`documents/chunks/images/captions_*/frames .jsonl` + `.npy`) with stable uuid5 ids. Stages are skippable and resumable, and OCR results are cached in `ocr_cache.jsonl`. Its per-doc rules (`page_doc`, `attachment_doc`, `doc_chunks`, `chunk_row`, caption text builders, `stable_id`) live in `service/index/doc_rules.py`, shared with `indexer`; change rules there, not in two places.
- `loader.py` loads artifacts into PG + Qdrant without re-embedding: documents upsert by url (keeps ids, so v1 points still resolve; v1 columns `content_hash`/`raw_s3_key` untouched), `media` (unique sha256) + `media_occurrence`, `videos` + `video_occurrence`, media files to S3/local store (`Storage.put_file`, hard link locally), then points, then checks counts. It refuses unless the target collections end in `_v2` and the manifest models match config.
- `loader` also builds the entity graph (D20, below) from the artifacts plus a re-parse of the snapshot HTML (for per-image context), and has `--media-only --upload-media` for the separate S3 upload step of the cutover.
- `indexer.py` is the single v2 write path (payload builders, PG upserts, `index_page`, `remove_document`). Image/frame points are one per file with `document_id` as a **list** of docs; deleting a doc only removes its id (`vector_store.detach_document`) and drops the point when no doc is left. Re-indexing a doc that was the only user of an image/video recreates those points from stored bytes. PG is shared by the blue/green collections and each compute extracted video frames at different times, so one video can carry several frame sets: `media.frame_sets` tags each frame row with the image collection(s) it belongs to (loader writes it; `loader --tag-frames` backfills a DB loaded earlier), and `indexer.pick_frame_set` only uses the serving collection's set, adopting exactly one old set when none exists (taking all rows had put 23 instead of 10 frames on one page, 2026-10-21). Old sets are removed by hand once the old collection is gone: `reconcile --prune-frames [--include-untagged] [--apply]` (plan only without `--apply`; nothing is pruned while the collection still exists; a video never loses all its frames; files on the store are kept). `vector_store.require_v2()` makes the v2 writers refuse a v1 collection.

**Query side** — `api/routes.py` (FastAPI, HTTP only): `POST /query`, `POST /chat` (SSE: status → sources → streamed answer deltas → `[DONE]`), `GET /media/{id}` (v1, `media_assets`), `GET /media/s/{sha256}` (v2, `media`; `Source.media_key`), static UI in `sict_crawler/api/ui/`. Both endpoints call `agent.run`: `retriever.retrieve` (via `query_rewriter`: abbreviation rules, the LLM rewrite only with `llm.rewrite_query` / `LLM_REWRITE_QUERY`, off by default since 2026-10-25; dense / keyword RRF fusion; CLIP for cross-modal media). The keyword leg (`vector_store.keyword_search`) is BM25 over accent-folded tokens as a Qdrant sparse vector `bm25` with `modifier=idf` (`core/sparse.py`, same tokenizer as `scripts/eval_retrieval.py`) on v2, legacy per-term `MatchText` on v1. `rerank_text` puts the question↔point cosine into `raw_score` (router caption threshold) — on v2/v3 from the stored vectors (`dense_score` kept through RRF, Qdrant `point_vectors` for BM25-only hits), never by re-embedding: re-embedding every caption cost ~16 s per question through the int8 service (2026-10-20) — but only reorders on v1: on v2, reordering by cosine discarded the BM25 signal (golden set on live Qdrant: R@5 0.94 → 0.97, MRR 0.81 → 0.87 without it). **Guardrails that do not depend on the LLM (D27, 2026-10-25):**
  - **The original question is always searched.** The rewrite adds a dense list and a BM25 list to the RRF only when it differs from the question after folding (`hybrid_search_text(alt_queries=…)`). By default the rewrite is the abbreviation rules (CNTT → công nghệ thông tin). The media leg uses the rewrite.
  - **The LLM rewrite is off by default** (`llm.rewrite_query`, 2026-10-25). It cost 2–11 s per question for no measured gain: golden recall@5 0.985 with and without it, MRR 0.898 without vs 0.888 with, list coverage 0.724 vs 0.736, media-mode accuracy 0.871 (rules) vs 0.886. Media intent now comes from the router rules.
  - **Parallel Qdrant calls (2026-10-25).** Before, a question made 9–20 sequential calls (0.1–3.7 s). Three thread-pool tiers are used, and a task only waits on a lower tier, so a full pool cannot deadlock:
    - stages (`retriever._STAGE_POOL`): query-image embedding, media leg (`_media_candidates`) and text leg;
    - legs (`vector_store.parallel`): dense / BM25 / graph / rewrite lists, and the media searches;
    - collections (`vector_store._per_collection`): text / ocr.
  - **Document diversity.** `retriever.diversify` keeps at most `retrieval.per_doc_max` (2) chunks per document in the top k. Chunks pushed out are ranked after, not dropped. `i2i-doc` chunks are exempt.
  - **Dominant document (D30, 2026-10-27).** When the top hit's document holds ≥ `retrieval.dominant_min` (6) of the first 10 hits before diversify, the question is about that document ("Chiến lược 2021–2025 là gì?", "Danh sách đề tài NCKH 2022" = one long table), so it may take up to `retrieval.dominant_doc_max` (4) chunks instead of `per_doc_max` (or 1 for list questions). It fires on 8/90 golden + list_v1 questions. Golden and list coverage are unchanged at min 6–7; min 5 lowered list coverage to 0.951.
  - **"Latest" questions (D30).** A question that is only a section plus "mới nhất / gần đây" (`filters.QueryFilters.latest`, e.g. "Thông báo mới nhất?") puts the newest documents of that section first (`vector_store.latest_text`: Qdrant filter on section + year, both indexed, sorted by `published_at` on the client, first chunk per document, attachments skipped). Semantic search cannot order by date: it returned a notice from 10/2025 instead of 05/10/2026. A question with other content ("thông báo mới nhất về học bổng") still only gets the soft recency boost.
  - **List questions** (`router.is_list_question`: "có những … nào", "danh sách", "gồm những ai"…) get at least `retrieval.list_top_k` (10) sources, one chunk per document, and `route.list_question` / `list_question` in the responses.
  - **The LLM gets each chunk's full text.** It is stored in `Source.content`, kept in the query cache, and stripped from HTTP responses (`routes.RESPONSE_EXCLUDE`). Before D27 it got only the 300-character `excerpt`. `sources.build_context` caps each source at min(`llm.source_chars` 1500, `llm.context_chars` 9000 / number of sources) and at least 400. List questions get `llm.list_context_chars` (15000) instead of `context_chars` (D29, 2026-10-26): at 900 characters per source, the list item often sat past the cut (list coverage 0.724 → 0.970 with the same 10 sources). MMR selection was tried and gave nothing (0.69–0.73), so selection stays `diversify`.
  - **One retrieval pass, no LLM judge.** A lexical fallback runs only when nothing is found.
  - **`sufficient` is a rule** (`agent.evidence`): there are sources, the best question↔chunk cosine (`Source.cosine` = `raw_score` or `dense_score`) is ≥ `retrieval.min_cosine` (0.45), and ≥ `retrieval.min_term_cover` (0.8) of the question's content tokens (folded, stopwords removed) appear in the context. These thresholds are provisional and were calibrated on 89 questions.
  - **Why the LLM judge was removed.** It could not see what was missing, so it rated incomplete lists "sufficient". It also rated 6/8 out-of-scope questions "sufficient", changed with the model, and cost 1–3 extra LLM calls per question.
  - **`eval/list_v1.jsonl`** has 12 list questions with `expected_items` and 8 out-of-scope questions (draft). Run `scripts/eval_api.py --list` to score item coverage in the LLM context and `sufficient` accuracy.
  - **With no LLM key**, `/chat` echoes the context. It also echoes when the model returns only reasoning: reasoning models (glm-5.3, deepseek via kiraai) spend 300–700 tokens thinking before answering, and the gateway ignores switches to turn that off, so `llm.max_new_tokens` defaults to 2048 (256 left no answer at all). `stream_answer` logs when that happens. The answer prompt says to answer what the context has and name what is missing, and to say "no information" only when no source is relevant.

  Query results and media bytes are cached best-effort in Redis **db 3** with TTLs (`repository/cache.py`; Redis runs `volatile-ttl`, so frontier keys without TTL are never evicted). The cache key prefix is `q:v6` (v4 by D27, v5 when the LLM rewrite was turned off and query images moved to 336, v6 for the dominant-document and latest rules of D30) and includes the filters and the serving collections (`retriever.index_tag`), so a v2 ↔ v3 cutover or rollback never serves the other index's cached results. The key does not include the LLM config: when measuring LLM on vs off, delete `q:v6:*` in Redis db 3 between runs (or start the variant with `REDIS_URL` pointing at a closed port, which turns the cache off), or the second run reads the first run's results. Responses carry `entities` (matched graph entities).
- **Entity graph** (D20; `graph.py` rules, `graphsync.py` the single build path; rules only). Postgres is the source of truth; never compute graph payloads elsewhere.
  - Extraction rules (no model, deterministic): persons = honorific/role prefix + Vietnamese surname, or ≥ 3 capitalised words; single-word stoplist only for words that are never names, plus `_NOT_NAME_BIGRAMS` ("thành phố", "trung tâm"…) because Thành/Trung/Tâm/Quốc… are common names. Events = quoted names and event-keyword phrases in titles / own alts (years stripped → yearly series is one entity). Clubs = "CLB …" keyed by acronym.
  - **Person keys keep diacritics** (`person_key`, tone mark normalised: thủy = thuỷ, but Hùng ≠ Hưng). Folding would merge different people. Unaccented question text matches only when unambiguous (single candidate, the staff member, or a dominant one). Staff from `/vn/html/can-bo-giang-vien/<slug>` profiles get `attrs.staff` (canonical list, AC-C7).
  - **Rule tightening 2026-10-18** (measured on `eval/graph_gold_v1.jsonl`): in article text a person match must be capitalised and the "middle + given name" alias needs thầy/cô/TS… right before it ("Tập đoàn Hồng Hải", "Cao đẳng khóa 21" are not people); a place word right before a name (Phường/THPT/đường/Đền thờ…, compared WITH diacritics so "Hiệu trưởng" still passes) blocks it; parser turns `<br>` inside table cells into "; " and `_clean_page` turns pdftotext column gaps (≥ 3 spaces) into " | " so adjacent names stop gluing; staff come from the profile title validated against the URL slug (82/82); rare surnames (An, Lù, Chảo, Quyền, Liêu…) added; "Đoàn" is a surname at the start of a name.
  - **Canonical catalog** `sict_crawler/service/graph/graph_catalog.yaml` (data, owner-reviewed; draft written 2026-10-18): clubs (HIT, IT Supporter, HEC, FIT Media, iStar, TNTN, SIP…) and event series (OLP, ICPC, PROCON, IT Festival, …) with aliases (accent-folded, matched in body text too) and `acronyms` (single token, case-sensitive and standalone in articles: "HIT" but not "hit"/"HIT_Titans"); rule mentions containing an alias are folded into the catalog entity (`Catalog.canon`), `block:` drops slogans/titles. `event_key` strips "Chung kết / Cuộc thi / Vòng chung kết" prefixes; titles over 12 words are not event names; trailing connectors are trimmed; lowercase quoted phrases are not events; an event whose key contains a ≥ 3-word event key seen in ≥ 2 docs is merged into it.
  - Relations: per-document evidence is damped (`REL_DOC_DAMP` 0.5: one shared photo → 0.5, two docs → 0.75); events/clubs seen in one doc and not in the catalog get no relations.
  - `Gazetteer.match(text, query=False)`: in documents, the "middle + given name" alias only counts when written as a proper noun or after thầy/cô/TS…, and single-token aliases (acronyms) are ignored ("người chiến thắng" ≠ Nguyễn Chiến Thắng, "Procon Việt Nam" ≠ NAPROCK PROCON). `query=True` (API) allows both. A person match nested inside a longer person match is dropped; other overlaps are allowed (a title can name "ngày hội CNTT" and "IT Festival").
  - Run-on name merge only when the extra word is a title or the next name's surname (`runon_tail`): "Nguyễn Thị Kim" + "Anh" is a different person.
  - `graphsync.rebuild` (loader, and nightly from incremental): reads docs / chunks (Qdrant) / `media_occurrence.context` / OCR from PG + Qdrant, applies reviewed `entity_aliases` (alias or block, stored as data), merges globally, writes `entities` / `entity_links` (per-chunk `mentions`, `roles`) / `entity_relations`, queues near-duplicate persons into `entity_review` (never auto-merged), then `sync_payloads`. `update_documents` does the same for a few docs in incremental (`resolve_mention` uses the same merge rules). `sync_payloads` rewrites `entities` / `entities_strong` from PG, diffs against Qdrant and groups points with identical payloads (one `set_payload` per point costs ~70 ms; grouped is ~0.2 s / 500 points).
  - Review loop: `graphsync review-export f.csv` → set status merged / distinct / blocked → `review-import` → `rebuild`. `review-import` matches rows by id, else by (kind, key, reason, candidate_key), so the reviewed files in `eval/review/` (`staff_pairs.csv`, `near_dup_pairs_2026-10-22.csv`: 7 merged, 759 distinct) re-apply on another DB (production) after its first `rebuild`. Quick fixes: `graphsync block event "học máy"`, `graphsync alias person "<variant>" "<canonical>"`.
  - LLM entity extraction (stage C, `graph_llm.py`) was removed on 2026-10-18 by owner decision: the graph is rules-only, `entity_links.roles` / `entity_relations.roles` stay empty, and the 1.504 earlier LLM results are archived in `/DATA/craw-sict-data/2026-10-16/llm/` (table `llm_extractions` dropped). Do not reintroduce LLM extraction without the owner asking.
  - Retrieval: `graph.match_question` (gazetteer + relations loaded at API startup, refreshed every 10 min) adds an entity-filtered dense list (AND list for ≥ 2 entities) to the RRF, entity-linked media (modality `graph`, `router.graph_min`) ahead of CLIP, drops CLIP-only media for person questions once the graph has media, and puts `[graph]` facts (related entities by kind, doc counts, roles) into the LLM context. Graph links describe text evidence, not face identification.
  - Evaluation (stage B): `eval/graph_gold_v1.jsonl` (150 stratified docs, self-contained text, `draft.rules` + blind `draft.llm` suggestions, `status: draft` until a human reviews per `eval/GRAPH_ANNOTATION.md`), `scripts/eval_graph.py --pred rules|llm|file`, CI gate `tests/test_eval_graph.py` on a 6-doc hand-labeled fixture.
- `reconcile.py` (AC-E6): nightly from incremental (Redis `reconcile:last`, every 20 h) — deletes orphan text points, detaches deleted doc ids from media points, resets `hash_v2` of docs missing points; aborts above 20% orphans (e.g. pointed at an empty DB).
- **Metadata filtering** (`filters.py`, D18): hard filters (`sections`, `doc_types`, `year_from/to`) apply only when the caller passes `QueryIn.filters`. Hints inferred from the question (section keywords, years, "mới nhất") only multiply scores via `apply_boost`, applied after rerank. Missing metadata is neutral. Qdrant payload indexes exist for `section`/`doc_type`/`year`.
- **Media router** (`router.py`, D17): `retrieve` returns `(text, media, route)`. Intent (`none|optional|required` plus `wants_file`) comes from the keyword rules in `classify_rules` (since 2026-10-25). With `llm.rewrite_query` on, it comes from the same LLM call that rewrites the question (`vlm.rewrite_and_route`, JSON), and the rules are the fallback, and rules can only raise the level (an explicit "ảnh/video" keeps `required`). `none` skips the media leg entirely and drops caption hits from the text sources. `gate` selects media by evidence: `optional` = only media whose `document_id`/`doc_id` is among the top text docs, max 3; per-modality raw-score thresholds (`config.yaml: router.clip_min/caption_min`, provisional), never RRF scores; one slot per video. Empty media is a valid answer and comes with a `media_note`. Watch out for Vietnamese folding collisions in keyword rules: "Lê" (surname) folds to "le" (lễ), "tại" to "tai" (tải), "tiếng Anh" to "anh" (ảnh).
- **Acceptance over HTTP** (`scripts/accept_api.py --api URL`, stdlib, after a deploy): U1–U6 (query images come from the API's own U2 results, perturbed with Pillow if installed), `/media/s/{key}`, D24 citations on `/chat` (SSE `citations` event, no phantom `[n]`), `/metrics`; exits 1 on any FAIL. Pair with `scripts/eval_api.py` (golden recall over HTTP). `/query`, `/chat` and the media endpoints run their synchronous work (`agent.run`, S3 reads) in the threadpool: called directly in the async handlers they serialised every request and blocked `/metrics` (Alloy scrape timed out → `up=0` on Grafana during a 4-worker load, 2026-10-21).
- **Evaluation**: `eval/golden_v1.jsonl` (70 questions with expected URLs, media mode, file flag) + `scripts/eval_retrieval.py` (offline on artifacts: dense / folded BM25 / hybrid / hybrid+boost, doc-level recall@5/10 and MRR@10). Run it before changing models, thresholds or chunking rules.
- **RAGAS** (`scripts/eval_ragas.py`, group `eval`, run by hand on the dev box against a live API): `collect` stores the real `/chat` answer and the context the LLM got (`/query` `context`, split on `---`) per question of golden + list_v1 into `<out>.answers.jsonl`; `score` runs faithfulness, answer_relevancy (embeddings from the embed service :8090), context_precision (reference-free, one LLM call per source) and context_recall (list_v1 only, `expected_items` as the reference) into `<out>.scores.jsonl` + `<out>.summary.json`. Both steps resume from what the files already hold. The judge defaults to `LLM_*` from `.env`, which is also the answering model (self-judging bias; override with `RAGAS_LLM_BASE/MODEL/KEY`). The free kiraai model allows 20 calls per minute shared by the API and the judge, so run the steps one after the other with `--rpm` ≤ 15. `/chat` falls back to echoing the context when the provider times out; `collect` waits 60 s and retries those. ragas 0.4.3 needs `langchain-community<0.4.2`.

## Multimodal + structure (D21–D23, 2026-10-17; code in, index v3 not built yet)

- **Embedding gateway** (`embedder.py`): `embedding.backend` = `torch` (default; E5 384-d + CLIP 512-d, index v2) or `api` (D22: one multimodal model, `jina-clip-v2` 1024-d, text and image share one space). `api` posts Jina-style `{model, input:[{text}|{image:b64}], normalized, dimensions}` to `EMBED_API_BASE/embeddings` (`EMBED_API_KEY`, `EMBED_MODEL`, `EMBED_DIM`, `EMBED_CACHE_PATH`). Cloud for the first preprocessing run, then a self-hosted ONNX int8 service behind the same interface: switching is config only. The remaining v3 vectors (images, captions, frames) were embedded 2026-10-20 by a temporary fp32 HF server on a Kaggle 2× T4 box (cosine vs cloud: text 0.9999, images 0.9996; HF `encode_text` must get `max_length=8192`, default 512 truncates long chunks). The self-hosted service is `sict_crawler/service/embedding/embed_server.py` (group `embed`: onnxruntime + onnx + onnx-ir + tokenizers, no torch; `Dockerfile.embed`, `docker-compose.embed.yml`, port 8090). `build_towers` (`python -m sict_crawler.service.embedding.embed_server build`, once, ~2.5 min, cached in `$HF_HOME/sict-embed/<rev>-w8`) takes the official fp32 `onnx/model.onnx` (+3.5 GB data) of `jinaai/jina-clip-v2` pinned to revision `e10d47f`, splits it into a text graph and a vision graph (the repo graph combines both towers and ORT does NOT prune the unused one: a short query cost as much as an image and RAM grew to OOM), and quantizes each tower to **weight-only int8** (MatMulNBits 8-bit, block 32; `accuracy_level` 4 for text = blockwise int8 activations, 0 for images) plus the 250k×1024 vocabulary table to per-row int8 (`quantize_vocab_table`; the ORT quantizer's Gather option bumps the opset and breaks the graph). Measured 2026-10-20 against the v3 vectors: the official `onnx/model_int8.onnx` text tower is broken (cosine 0.54–0.61; images 0.98), dynamic int8 with int8 activations is worse (0.36; the text tower has large activation outliers), weight-only int8 gives text 0.9990, queries 0.9995, images 1.0000. `onnx` refuses external data reached through a symlink (HF cache) or a hardlink, so the build copies the fp32 files into a temp dir. No `attention_mask` input → texts are batched only with others of the same token length. On the production target (2 vCPU / 8 GB): idle 1.33 GB, one query ~0.3 s (fp32 is 0.25 s: the ~560M-param text tower is compute-bound on 2 vCPU, so int8 saves RAM, not time), one image ~9 s, `retrieve` without LLM ~0.4 s; attention is full (no flash) so peak RAM grows with length² (2048 tokens 3.5 GB, 4096 → 6.9 GB, the longest v3 chunk at 5,201 OOMs) → defaults `EMBED_TEXT_MAX_LEN=2048`, `EMBED_TOKEN_BUDGET=2048`, `EMBED_CONCURRENCY=1`, `mem_limit` 6 GB (only 77/16,794 chunks exceed 2048 tokens, the same 77 that exceed 4096). Requests run in three ORT lanes (`Lanes`, `lane_of`: one short text = query, one image = user upload, anything else = bulk), each `EMBED_CONCURRENCY` wide, so a query never queues behind an incremental batch: measured 2026-10-21 on 2 vCPU, one shared lane made a query wait ~80 s behind an 8-image request, and two overlapping batches timed out the client, which resent them while the server was still computing; with lanes a query takes 0.5 s next to a batch. Image batching on CPU is not faster (8 images in one run 80.8 s, 8 runs of 1 image 73.5 s), so `EMBED_IMAGE_BATCH` defaults to 1; the client timeout grows with the images and the text length in a request (`embedder.IMAGE_TIMEOUT_S`, `TEXT_TIMEOUT_S_PER_KCHAR`: long text costs ~8.4 s per 1,000 characters on 2 vCPU, so a 32-chunk attachment batch takes minutes and the fixed 120 s timeout made incremental resend it). Throughput on the 2 vCPU target is CPU-bound: ~0.45 s per text question, ~9.7 s per image at 512. **Query images run at 336** (owner decision 2026-10-25; 392 from 2026-10-22; corpus images stay 512, so nothing is re-embedded). Measured on the int8 service: 40 cropped and recompressed images, 336 takes 4.26 s per image vs 392 at 6.09 s; the original ranks 1st in 40/40 vs 39/40; lowest cosine 0.783, above `i2i_min` 0.6. The service builds every size listed in `EMBED_QUERY_IMAGE_SIZES` (default 336, `336,392` keeps both), and the API sends `EMBED_QUERY_IMAGE_SIZE=336`. The tower cache dir must be writable by the container user, or startup fails with PermissionError on `image_<size>.onnx.tmp`. Details: the vision graph exported at 512 hardcodes a 36×36 patch grid, and `resize_vision_tower` rewrites it in place for another size — bicubic-interpolated `pos_embed` (numpy `bicubic_matrix`, matches torch `F.interpolate` to 1e-5), RoPE cos/sin tables recomputed with `rope_tables` (the formula is checked by rebuilding the original 36×36 tables; a mismatch raises), and the 1296/1297 shape constants. `query_towers` builds `image_<size>.onnx` from the quantized `image.onnx` at startup (3 s, `EMBED_QUERY_IMAGE_SIZES`, default 336); the result equals the PyTorch tower at 392 (cosine 1.0000). A query image item carries `"image_size": 392`, which the client sends only with `embedding.query_image_size` / `EMBED_QUERY_IMAGE_SIZE` set (only for the self-hosted service; Jina cloud does not know the key) and only through `embedder.embed_query_image_base64` (cache kind `iq<size>`, so a query vector never lands in the corpus). Measured: 512 → 392 cuts an image from 9.6 s to 5.3 s; on 40 images vs the 5,962 index vectors the original ranks 1st in 39/40 (top 5 40/40), cosine to the 512 vector of the same image 0.983 (448: −37 %, no loss; 336: −66 %, min cosine 0.94). HTTP acceptance 54/54; 4 concurrent image questions p50 35 s → 20 s. Idle RAM 1.67 GB with the third tower. Image preprocessing reimplements JinaCLIPImageProcessor (shortest side 512 bicubic, center crop, CLIP mean/std), and the repo `tokenizer.json` ships fixed padding/truncation at 77 so `load_tokenizer` disables padding and truncates at 8192. int8 does not reproduce fp32 vectors: before pointing the API or incremental at it, `scripts/embed_parity.py --base http://host:8090/v1` must PASS (cosine vs v3 artifacts, top-10 overlap of golden queries) and the golden eval on Qdrant v3 must hold. Queries get `embedding.query_prefix`, corpus gets none. Images are resized to 512 px JPEG before sending; `embed_image_bytes` still returns `(vecs, ok_idx)`. Vectors are cached in sqlite by input hash; endpoint failures raise `EmbedError` (never skip a vector). `scripts/embed_pilot.py` samples the endpoint, prints token usage and the full-corpus estimate, then stops: never run the full compute before the owner agrees. Index v3 = three collections (owner decision 2026-10-20): `QDRANT_COLLECTION_TEXT/IMAGE/OCR=sict_text_v3/sict_image_v3/sict_ocr_v3` — text = page/file chunks (scanned-PDF OCR stays here to keep page numbers), image = image + video-frame vectors, ocr = `media_caption` points (title + section + OCR text, video subtitles), same dense space + sparse BM25. `qdrant.collection_ocr` empty = captions share the text collection (v1/v2). Go through `vector_store.ocr_collection()` / `text_collections()` / `collection_for(payload)`: searches with no `collection` cover all text collections (dense merged by cosine, BM25 interleaved by rank because IDF is per collection), deletes/reconcile/graph payload sync cover both, `QDRANT_TEXT_DIM=QDRANT_IMAGE_DIM=EMBED_DIM`; `loader.check` compares backend/model/dim/prefix with the artifact manifest and accepts `_v2`/`_v3`.
- **Use cases** (`retriever.retrieve`, backend `api`): U1 text→text, U2 text→image, U3 image→image, U4 image→text, U5–U7 text+image→text/image/both (acceptance AC-U1..U10). The query image searches the image collection (`via=i2i`, `rc.i2i_min`, exempt from the "belongs to top text docs" rule), the text collection (`via=i2t`) and pulls chunks of the document holding the similar image (`via=i2i-doc`). With an empty question the route is `required` and returns both. Thresholds are per pair (`t2i_min`, `t2c_min`, `i2i_min`, `i2t_min`) and provisional. `Route.inputs/outputs` and `Source.via/heading_path` are in the responses. The user's image reaches the answering LLM only with `llm.answer_with_image`. The `torch` backend keeps the old behaviour (image = one more CLIP vector). The query cache key now includes a hash of the image.
- **Page structure** (`parser.build_blocks`, D23): `ParsedPage.blocks` = DOM-ordered blocks (heading with level and `heading_path`, paragraph, list, quote, table, image, video, attachment). Markdown and `hash_v2` are unchanged (checked on 396 real pages). `chunking.structured` (`CHUNK_STRUCTURED`) builds chunks from blocks (`indexing.build_chunks_structured`): chunks carry `heading_path` and `block_range`, tables inherit the section heading and the text after a table keeps it, oversize blocks split by sentence without embedding. `documents.structure` (outline, `indexing.outline`) and `documents.hash_struct` store the layout; `media_occurrence.block_idx/heading_path` and `video_occurrence.block_idx` record where media sit. Incremental re-indexes a page when `hash_v2` or `hash_struct` changes; a page without `hash_struct` (indexed before D23) only gets its structure written. Raw HTML/media/attachments live in the object store (MinIO via `S3_ENDPOINT_URL`, or the local store); Postgres keeps the source of truth (documents, structure, object keys).

- **Citations and pages** (D24): `ix.extract_file_pages` returns `[(page, text)]` (PDF split on pdftotext `\f`, PPTX per slide in numeric order, scanned PDF per OCR page, docx/xlsx → `page=None`); `extract_file_text` is its join. With `chunking.structured`, attachments are chunked per page (`build_chunks_paged`, `[trang N]` marker, payload `page`). `sources.build_context` numbers sources `[1]…[n]` (text first, then media) with `Source.cite` ("Tên file — trang N" for files, "Tiêu đề › Mục" for pages); `citations.enforce` (pure) drops phantom `[n]` and appends a `Nguồn:` footer when the answer cites nothing; `/chat` emits a `citations` event before `[DONE]`, `/query` returns `citations`. For an uploaded image, `retriever._linked_doc_hits` maps similar images to their document and takes the chunks around the image's block (`_image_block` reads `block_idx` from the image's caption point, `_chunks_around` picks the chunk containing it or its neighbours), falling back to the chunk most similar to the image vector.

## Configuration

`config.yaml` (path overridable with `SICT_CONFIG`) is loaded into dataclasses in `config.py` via `get_settings()`. Env vars override yaml for deploys: `POSTGRES_DSN`, `REDIS_URL`, `QDRANT_HOST/PORT/GRPC_PORT/TIMEOUT`, `LLM_API_BASE/MODEL/KEY`, `VLM_*`, `AWS_PROFILE` or `AWS_ACCESS_KEY_ID/SECRET`, `S3_ENDPOINT_URL` (MinIO). `embedding.device` is `auto` by default: `embedder.get_device()` resolves it once (CUDA if torch sees a GPU, otherwise CPU, and forced `cuda` without a GPU falls back to CPU). `EMBED_DEVICE` overrides it. Always use `get_device()`, never read the config value directly. Without AWS creds, `storage.Storage` falls back to local disk (`SICT_LOCAL_STORE`, default `./_local_store`). Schema migrations are ad hoc: `db.init_db()` does `create_all` plus `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, so add new columns there.

## Production hardening plan (decided 2026-10-12, not yet implemented)

`plan.md` is the source of truth: decisions D1–D19, stages 0–5, verify and rollback per stage. Acceptance criteria live in `tests/acceptance_*.md` (groups AC-H, AC-O, AC-P, router/filter AC-R8–R12, plus additions to E/S/G). New code should move toward these decisions, not away from them:
- **Parser and site theme**: the site uses an `irs-*` theme. Main content is `div.irs-blog-single-col` or `section.irs-blog-single-field div.col-md-8`, and the sidebar is `irs-side-bar`. The old index was built before the parser matched this theme, so it contains whole pages with sidebar images, video and view counters, which explains the image/video duplication. The parser now also strips `irs-info-text` (date and view counter) after reading the date. Parser changes must come with real-HTML fixtures (`tests/fixtures/`, `test_parser_theme.py`). Incremental now uses the same rules (`indexer.index_page`).
- Media is moving to `media` (unique by sha256) + `media_occurrence`, with video keyed by YouTube id. OCR state becomes explicit columns (`ocr_status`) instead of parsing `sub:`/`ocr:` markers in captions.
- **Qdrant stays the vector store** (D8; pgvector was considered and rejected). Postgres holds metadata and relations only. Consistency between them relies on deterministic uuid5 point ids from `compute.py` artifacts, so upserts overwrite instead of duplicating, plus a nightly reconcile. Accent-insensitive keyword search uses sparse BM25 on folded tokens (replaces the earlier `text_folded` + full-text-index draft, which only filters and cannot rank). Cutover is blue/green via the `*_v2` collections (config default); rollback = point the API's `QDRANT_COLLECTION_TEXT/IMAGE` back to `sict_text`/`sict_image`. Schema changes still go through `db.init_db` ALTERs; Alembic is deliberately deferred until a breaking (rename/drop) schema change, since v2 only adds tables/columns.
- Embeddings are moving to **ONNX Runtime int8** with no torch in either image. The CLIP text side becomes `clip-ViT-B-32-multilingual-v1`, which shares the CLIP B/32 image space, so image vectors stay valid. Keep the `embedder` function signatures stable.
- Schema changes go through Alembic from stage 3 on (not `db.init_db` ALTERs).
- Hardware is 2× c7i-flex.large (2 vCPU / 4 GB). Keep the sum of `mem_limit` per VM within physical RAM. API runs one uvicorn worker (each worker reloads the models).
