# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Multi-modal RAG crawler for `https://sict.haui.edu.vn/vn`: crawls the site tree → text, tables, images, video keyframes → PostgreSQL + Qdrant + S3, then serves a RAG Q&A API + chat UI. Code comments, docs and commit-facing text are mostly Vietnamese; keep that convention.

## Fixing quality problems (owner rules, 2026-11-02)

These apply to retrieval, ranking, prompt and indexing fixes found while investigating a failing question or eval case.

1. **A fix found for one problem is provisional until it is checked against the other cases.** After investigating and proposing a fix, check before applying it whether it lowers quality on other cases. Measure it against the whole eval suite (golden_v1, golden_v2, list_v1, plus RAGAS when the answer changes), not only the case that motivated it, and report any case that gets worse.
2. **Prefer general fixes over case-specific ones.** Aim for a change that fixes the class of problem: ranking structure, chunking, fusion. Avoid keyword lists, one-section rules or thresholds tuned to one question. A small, case-level change is acceptable only when all three hold:
   - it is clearly small;
   - it does not affect the rest of the system;
   - it still improves overall performance.

   Even then, propose it with the measurements and wait for the owner to approve it before applying.

## Architecture

**Ingest pipeline** — `frontier` (Redis BFS queue `frontier:list`, `frontier:seen` dedup, per-host politeness) → `crawler.fetch` → `parser` (markdown, tables, image/video URLs) → `chunker` (token budget, optional semantic splitting via E5) → `embedder` (E5 multilingual-small 384-d for text, CLIP ViT-B/32 512-d for images) → `vector_store` (Qdrant `sict_text`, `sict_image`) + `db`/`models` (PG: `documents`, `chunks`, `media_assets`) + `storage` (S3).

- `main._process_page` is the core per-page unit and delegates to `indexer.index_page` (index spec v2, same rules and uuid5 ids as bulk compute). It is idempotent: `documents.hash_v2` (sha1 of the cleaned markdown, not raw HTML, whose view counter changes on every fetch) unchanged → skip; changed → set `hash_v2=NULL` and commit, remove the doc's points, then rewrite. Listing pages are not indexed but their links are pushed (pagination keeps depth). `incremental.py` reuses it. `--rechunk`, `--videos-backfill` and `--annotate-ocr` are v1-only and refuse to run against a v2 collection.
- `crawler.fetch` backend via `CRAWLER_BACKEND` (`auto|httpx|obscura|crawl4ai`). `auto` = httpx first, Obscura CLI (`crawler_obscura.py`) if the HTML looks like a JS shell, crawl4ai last.
- **Images**: stored S3-only (`base64_data` in PG is now `""`; older rows may still have base64, so readers check base64 first then S3). Alt text becomes the initial caption.
- **Video** (`video.py`): ffmpeg scene keyframes (max 20, CLIP-deduped) stored as `kind=video_frame` and retrieved like images. Transcript is **subtitle-only** via yt-dlp (no ASR/Whisper). Never store full videos. YouTube cookies come from `$YT_COOKIES` (mounted `./cookies/`, rotated via `.github/workflows/cookies.yml`; never commit cookies).
- **Captions** (`annotate_ocr.py`): caption = doc title + Tesseract OCR text, embedded with E5 into `sict_text` as `kind=media_caption`. Video frames of the same video share one aggregated caption point. Face recognition and VLM captioning were removed (`vlm.enabled: false`); `vlm.py` is still used for LLM answer streaming and query rewriting.
- **Incremental** (`incremental.py`, D31: every 12 h, `crawl.cycle_budget_sec` 300 s from the start of the run for drain + recheck; past it both stop and the rest waits for the next run; the budget starts once the stores answer): wait for Postgres / Redis / Qdrant (`wait_for_services`, up to `crawl.startup_wait_sec` 900 s; after a reboot the worker starts minutes before the stores, and that run used to fail and sleep 12 h; still down → no stage runs, error heartbeat) → mark the URL of every document in PG as seen in `frontier:seen` (`mark_known_seen`; documents loaded by `loader` never went through the frontier, so every new post queued dozens of known pages again) → discover new URLs from seeds → **refresh every listing section** (`refresh_listings`: seeds + sections derived from article URLs in PG + listing URLs in `frontier:seen`, fetched directly every run because `frontier:seen` never expires; page 2, 3… only while the page still has unknown posts of that section, capped by `crawl.listing_max_pages`) → drain the frontier (new posts first) → recheck the N oldest non-attachment docs (50 per run). Drain records transient failures (timeout, 5xx, empty body, processing error) in `frontier:fails` / `frontier:retry` and re-queues them at the start of the next drain, up to `crawl.max_fetch_retries`; 404/410 is final. OCR now runs inline while indexing (`media.ocr_status`); the separate OCR stage only runs against v1 collections. Safety rules: only HTTP 404/410 delete a doc (`should_delete`, via `indexer.remove_document`: Postgres delete + commit first, then Qdrant, so a failure leaves orphan points rather than a doc without points), and a mass-delete guard aborts the pass past an absolute/relative threshold (`mass_delete_abort` → `MassDeleteAbort`; before 2026-10-14 the per-doc `except` swallowed it). Stages are isolated; heartbeat written to Redis `incremental:last_ok` / `incremental:last_error`. Qdrant writes go through `_with_retry`; `ensure_payload_indexes()` creates `document_id` integer indexes (deletes are slow without them).

**Bulk index path** (snapshot → compute → `loader`; config defaults to the `*_v2` collections):
- `snapshot.py` downloads only: HTML (gz), content-region images, attachment files, and a video list into `_snapshot/<date>/`, with state in `state.sqlite`. It crawls only the SICT host. Pagination links keep the parent depth, because the site only links to the next page and depth-limited BFS would otherwise stop after about 5 listing pages per section. `state.sqlite` runs in WAL mode so read-only inspection does not lock the crawler. Open it with `?mode=ro`. `frontier.canonicalize` forces https and strips the trailing slash, because the site mixes both and pages were otherwise fetched twice.
- `indexing.py` is index spec v2 and the single rule set for both bulk compute and (to be switched) incremental. It covers metadata (`section`, `doc_type`, `published_at`, `year`), markdown cleaning, context-header chunks, table chunks that repeat the header row (a table whose normal split yields a piece over 2×`max_tokens` — layout tables built from merged cells, e.g. one 2019 page with a 389-column row — is re-split compactly: empty cells and `---` rows dropped, a header longer than `max_tokens/4` not repeated, long rows split by cell groups; every other table stays byte-identical, so applying it on 2026-10-21 changed one document only: 80 → 10 chunks), a boilerplate hash, and attachment text (`pdftotext` and stdlib zip-XML; no extra deps).
- Attachments: the site serves files with wrong extensions (xlsx named `.xls`, docx named `.doc`), so `indexing.sniff_format` decides by magic bytes. Legacy OLE2 doc/xls go through `catdoc`/`xls2csv` (apt `catdoc`, in the worker image). Scanned PDFs are OCRed page by page with `OMP_THREAD_LIMIT=1` when `ocr_scanned=True`, which compute sets. The snapshot gives up on a host after 5 consecutive connection errors (dead legacy domains). For long snapshot runs, use the Docker container `sict-snapshot` (`--restart unless-stopped`, idles after finishing): the dev box reboots and kills plain background processes.
- `compute.py` turns a snapshot into store-agnostic artifacts (`documents/chunks/images/captions_*/frames .jsonl` + `.npy`) with stable uuid5 ids. Stages are skippable and resumable, and OCR results are cached in `ocr_cache.jsonl`. Its per-doc rules (`page_doc`, `attachment_doc`, `doc_chunks`, `chunk_row`, caption text builders, `stable_id`) live in `service/index/doc_rules.py`, shared with `indexer`; change rules there, not in two places.
- `loader.py` loads artifacts into PG + Qdrant without re-embedding: documents upsert by url (keeps ids, so v1 points still resolve; v1 columns `content_hash`/`raw_s3_key` untouched), `media` (unique sha256) + `media_occurrence`, `videos` + `video_occurrence`, media files to S3/local store (`Storage.put_file`, hard link locally), then points, then checks counts. It refuses unless the target collections end in `_v2` and the manifest models match config.
- `loader` also builds the concept graph (D33, below) once the points are written, re-parses the snapshot HTML for per-image context (`media_occurrence.context`), and has `--media-only --upload-media` for the separate S3 upload step of the cutover.
- `indexer.py` is the single v2 write path (payload builders, PG upserts, `index_page`, `remove_document`). Image/frame points are one per file with `document_id` as a **list** of docs; deleting a doc only removes its id (`vector_store.detach_document`) and drops the point when no doc is left. Re-indexing a doc that was the only user of an image/video recreates those points from stored bytes. PG is shared by the blue/green collections and each compute extracted video frames at different times, so one video can carry several frame sets: `media.frame_sets` tags each frame row with the image collection(s) it belongs to (loader writes it; `loader --tag-frames` backfills a DB loaded earlier), and `indexer.pick_frame_set` only uses the serving collection's set, adopting exactly one old set when none exists (taking all rows had put 23 instead of 10 frames on one page, 2026-10-21). Old sets are removed by hand once the old collection is gone: `reconcile --prune-frames [--include-untagged] [--apply]` (plan only without `--apply`; nothing is pruned while the collection still exists; a video never loses all its frames; files on the store are kept). `vector_store.require_v2()` makes the v2 writers refuse a v1 collection.

**Query side** — `api/routes.py` (FastAPI, HTTP only): `POST /query`, `POST /chat` (SSE: status → sources → streamed answer deltas → `[DONE]`), `GET /media/{id}` (v1, `media_assets`), `GET /media/s/{sha256}` (v2, `media`; `Source.media_key`), static UI in `sict_crawler/api/ui/` (chat layout since 2026-11-05: centred column, pill composer, greeting with example chips, image lightbox, faded HaUI logo watermark; under an answer: media grid, then citations grouped per page ("[11]–[16] Title"), then file actions; the list of every retrieved text source is not shown (owner 2026-11-05: one source list only, the citations); the logos are the school's own SVGs served by `GET /ui/{name}` from an allowlist; the answer is markdown: `md.js` renders it without a library, escaping all text before building tags, links http(s) only, `[n]` linked to source n; `index.html` loads the scripts with `?v=N`, bump it when changing JS because `/app.js` and `/md.js` are cached 1 h). Both endpoints call `agent.run`: `retriever.retrieve` (via `query_rewriter`: abbreviation rules, the LLM rewrite only with `llm.rewrite_query` / `LLM_REWRITE_QUERY`, off by default since 2026-10-25; dense / keyword RRF fusion; CLIP for cross-modal media). The keyword leg (`vector_store.keyword_search`) is BM25 over accent-folded tokens as a Qdrant sparse vector `bm25` with `modifier=idf` (`core/sparse.py`, same tokenizer as `scripts/eval_retrieval.py`) on v2, legacy per-term `MatchText` on v1. `rerank_text` puts the question↔point cosine into `raw_score` (router caption threshold) — on v2/v3 from the stored vectors (`dense_score` kept through RRF, Qdrant `point_vectors` for BM25-only hits), never by re-embedding: re-embedding every caption cost ~16 s per question through the int8 service (2026-10-20) — but only reorders on v1: on v2, reordering by cosine discarded the BM25 signal (golden set on live Qdrant: R@5 0.94 → 0.97, MRR 0.81 → 0.87 without it). **Guardrails that do not depend on the LLM (D27, 2026-10-25):**
  - **The original question is always searched.** The rewrite adds a dense list and a BM25 list to the RRF only when it differs from the question after folding (`hybrid_search_text(alt_queries=…)`). By default the rewrite is the abbreviation rules (CNTT → công nghệ thông tin). The media leg uses the rewrite.
  - **The LLM rewrite is off by default** (`llm.rewrite_query`, 2026-10-25). It cost 2–11 s per question for no measured gain: golden recall@5 0.985 with and without it, MRR 0.898 without vs 0.888 with, list coverage 0.724 vs 0.736, media-mode accuracy 0.871 (rules) vs 0.886. Media intent now comes from the router rules.
  - **Parallel Qdrant calls (2026-10-25).** Before, a question made 9–20 sequential calls (0.1–3.7 s). Three thread-pool tiers are used, and a task only waits on a lower tier, so a full pool cannot deadlock:
    - stages (`retriever._STAGE_POOL`): query-image embedding, media leg (`_media_candidates`) and text leg;
    - legs (`vector_store.parallel`): dense / BM25 / graph / rewrite lists, and the media searches;
    - collections (`vector_store._per_collection`): text / ocr.
  - **Document diversity.** `retriever.diversify` keeps at most `retrieval.per_doc_max` (2) chunks per document in the top k. Chunks pushed out are ranked after, not dropped. `i2i-doc` chunks are exempt.
  - **Dominant document (D30, 2026-10-27).** When the top hit's document holds ≥ `retrieval.dominant_min` (6) of the first 10 hits before diversify, the question is about that document ("Chiến lược 2021–2025 là gì?", "Danh sách đề tài NCKH 2022" = one long table), so it may take up to `retrieval.dominant_doc_max` (4) chunks instead of `per_doc_max` (or 1 for list questions). It fires on 8/90 golden + list_v1 questions. Golden and list coverage are unchanged at min 6–7; min 5 lowered list coverage to 0.951.
  - **"Latest" questions (D30).** A question that is only a section plus "mới nhất / gần đây" (`filters.QueryFilters.latest`, e.g. "Thông báo mới nhất?") puts the newest documents of that section first (`vector_store.latest_text`: Qdrant filter on section + year, both indexed, sorted by `published_at` on the client, first chunk per document, attachments skipped). Semantic search cannot order by date: it returned a notice from 10/2025 instead of 05/10/2026. A question with other content ("thông báo mới nhất về học bổng") still only gets the soft recency boost.
  - **List questions** (`router.is_list_question`: "có những … nào", "danh sách", "gồm những ai"…) get at least `retrieval.list_top_k` (10) sources, one chunk per document, and `route.list_question` / `list_question` in the responses. With `retrieval.list_neighbor_docs` (2, 2026-11-03) the chunks right before and after the chosen chunk of the first 2 documents are added after the main sources (`retriever.list_neighbors`, `via=neighbor`; ranking unchanged): the chunk that matches a list question best is often the introduction, and the list sits in the next chunk (list_v2 0.798 → 0.878).
  - **The LLM gets each chunk's full text.** It is stored in `Source.content`, kept in the query cache, and stripped from HTTP responses (`routes.RESPONSE_EXCLUDE`). Before D27 it got only the 300-character `excerpt`. `sources.build_context` caps each source at min(`llm.source_chars` 2200, `llm.context_chars` 11000 / number of sources) and at least 400. List questions get `llm.list_context_chars` (31000) instead of `context_chars` (D29, 2026-10-26): at 900 characters per source, the list item often sat past the cut (list coverage 0.724 → 0.970 with the same 10 sources). MMR selection was tried and gave nothing (0.69–0.73), so selection stays `diversify`. Raised 2026-11-03 from 1500 / 9000 / 15000: 74% of v3 chunks are longer than 1500 characters (median ~1,940), so most sources lost their last quarter; 2200 fits a whole chunk (list_v2 0.724 → 0.798, golden unchanged, list context ~13k → ~18k characters with the neighbours).
  - **Unaccented questions** (`retrieval.restore_accents`, 2026-11-03): jina-clip-v2 does not understand Vietnamese without diacritics (golden_v1 with accents stripped: recall@5 1.0 → 0.881, MRR 0.928 → 0.775), and folded BM25 cannot make up for it ("co", "de", "tai" are too common). `retrieval.accent.maybe_restore` restores the accents of a question that has none (≥ 2 restorable syllables) with a syllable bigram model built from the corpus itself (`accent_vi.json.gz`, Viterbi, digits / acronyms / capitals kept, 96.7% syllables right; rebuild with `python -m sict_crawler.service.retrieval.accent build` after a reindex) and no LLM. Only the dense leg uses the restored text; BM25 keeps the original (both fold to the same tokens). Measured: unaccented golden_v1 0.881 → 0.985 / MRR 0.775 → 0.920; accented questions unchanged.
  - **Proper-name phrases** (2026-11-05). Dense search places names by sound, so "Phạm Văn Tùng" lands near Nguyễn Thanh Tùng at cosine 0.53–0.62. The chunk that holds the name scores 0.37–0.45 and falls outside the top 200. BM25 does not help: "pham", "van" and "tung" occur in 21 %, 34 % and 6 % of points ("phẩm", "vấn", "từng" fold to the same tokens). Of the 8,464 names in the corpus, 78 % appear in one document only, so the concept graph cannot hold them.
    - **Extraction.** `query_rewriter.name_phrases` takes runs of ≥ 2 consecutive words written with a leading capital and the rest lowercase. It skips the first word of the question unless the whole question is the name, and it breaks the run on punctuation, digits and all-caps or mixed-case acronyms. For example, "TS. Nguyễn Bá Nghiễn" gives "Nguyễn Bá Nghiễn", while "Năm 2026 Trường CNTT" and "HaUI.No_Solution_AI" give nothing.
    - **Retrieval.** Each phrase adds one dense list and one BM25 list to the RRF, both restricted to points whose text contains the whole phrase. The restriction is `vector_store.phrase_filter`, a `MatchPhrase` on a text index with `phrase_matching` over `content` / `caption` (`_TEXT_INDEX_FIELDS`, created by `ensure_payload_indexes`). The function counts first (~0.01 s); a phrase with no matches, or with ≥ 200 points in one collection ("Hà Nội" 2,592, "Trường Công" 1,296), adds no list. One list was not enough: a single list contributes 1/61 to the RRF, which loses to chunks found by 3 lists (person_v1 hit@8 0.925 with one list, 0.975 with two).
    - **Cosine through RRF.** `_rrf` now copies `dense_score` from any dense list that contains the hit. Before, a hit that reached the RRF first through BM25 kept `cosine=None`.
    - **Evidence.** `agent.evidence` returns `sufficient` = False when a name phrase does not appear whole in the context. The comparison is folded; scattered tokens of the name no longer count.
    - **Measured** (develop vs branch, same index, cache off). golden_v1 R@5 1.0 / MRR 0.947, unchanged. golden_v2 url_hit 71 → 72/80 and MRR 0.731 → 0.738 (g084 "Information Technology" None → 2). list_v2 0.94 (38/42), unchanged. `eval/person_v1.jsonl` (40 questions + 4 names not in the corpus) hit@8 0.650 → 0.975 and MRR 0.577 → 0.933; names mentioned only in an article body went 10 → 21/22. `sufficient` flipped on 0 questions of golden_v1, golden_v2 and list_v2. On person_v1 it was right for 29 → 39/44 questions, and the 4 unknown names now all get False. A question with no name runs no extra Qdrant call. A question with a name runs 2 counts + 2 searches per phrase in `vector_store.parallel`, about +0.03 s p50 when warm.
    - **Limits.** Unaccented names ("Chu Thi Lan Anh") do not match the accented index. p29 is ranked 1st but stays `sufficient` False: the name sits past the per-source context cut (11000 / 8 sources).
  - **One retrieval pass, no LLM judge.** A lexical fallback runs only when nothing is found.

The query cache key now includes a hash of the image.
- **Page structure** (`parser.build_blocks`, D23): `ParsedPage.blocks` = DOM-ordered blocks (heading with level and `heading_path`, paragraph, list, quote, table, image, video, attachment). Markdown and `hash_v2` are unchanged (checked on 396 real pages). `chunking.structured` (`CHUNK_STRUCTURED`) builds chunks from blocks (`indexing.build_chunks_structured`): chunks carry `heading_path` and `block_range`, tables inherit the section heading and the text after a table keeps it, a short paragraph (≤ `TABLE_LABEL_MAX_TOKENS` 24) right before a table becomes the label of every piece of that table (`[Bảng: NĂM 2021]`; it used to be a chunk of its own and the table pieces did not know their year, so "bài báo năm 2021" missed: 152/1,932 pages, 365 chunks, re-indexed on the dev box 2026-11-01), oversize blocks split by sentence without embedding. `documents.structure` (outline, `indexing.outline`) and `documents.hash_struct` store the layout; `media_occurrence.block_idx/heading_path` and `video_occurrence.block_idx` record where media sit. Incremental re-indexes a page when `hash_v2` or `hash_struct` changes; a page without `hash_struct` (indexed before D23) only gets its structure written. Raw HTML/media/attachments live in the object store (MinIO via `S3_ENDPOINT_URL`, or the local store); Postgres keeps the source of truth (documents, structure, object keys).

- **Citations and pages** (D24): `ix.extract_file_pages` returns `[(page, text)]` (PDF split on pdftotext `\f`, PPTX per slide in numeric order, scanned PDF per OCR page, docx/xlsx → `page=None`); `extract_file_text` is its join. With `chunking.structured`, attachments are chunked per page (`build_chunks_paged`, `[trang N]` marker, payload `page`). `sources.build_context` numbers sources `[1]…[n]` (text first, then media) with `Source.cite` ("Tên file — trang N" for files, "Tiêu đề › Mục" for pages); `citations.enforce` (pure) turns full-width `【n】`/`［n］` into `[n]` (gpt-oss cites that way; 23/88 golden_v2 answers got a needless footer before 2026-11-02), drops phantom `[n]` and appends a `Nguồn:` footer when the answer cites nothing; `/chat` emits a `citations` event before `[DONE]`, `/query` returns `citations`. For an uploaded image, `retriever._linked_doc_hits` maps similar images to their document and takes the chunks around the image's block (`_image_block` reads `block_idx` from the image's caption point, `_chunks_around` picks the chunk containing it or its neighbours), falling back to the chunk most similar to the image vector.

## Configuration

`config.yaml` (path overridable with `SICT_CONFIG`) is loaded into dataclasses in `config.py` via `get_settings()`. Env vars override yaml for deploys: `POSTGRES_DSN`, `REDIS_URL`, `QDRANT_HOST/PORT/GRPC_PORT/TIMEOUT/API_KEY`, `LLM_API_BASE/MODEL/KEY`, `VLM_*`, `AWS_PROFILE` or `AWS_ACCESS_KEY_ID/SECRET`, `S3_ENDPOINT_URL` (MinIO). `embedding.device` is `auto` by default: `embedder.get_device()` resolves it once (CUDA if torch sees a GPU, otherwise CPU, and forced `cuda` without a GPU falls back to CPU). `EMBED_DEVICE` overrides it. Always use `get_device()`, never read the config value directly. Without AWS creds, `storage.Storage` falls back to local disk (`SICT_LOCAL_STORE`, default `./_local_store`). Schema migrations are ad hoc: `db.init_db()` does `create_all` plus `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, so add new columns there.

## Production hardening plan (decided 2026-10-12, not yet implemented)

`plan.md` is the source of truth: decisions D1–D19, stages 0–5, verify and rollback per stage. Acceptance criteria live in `tests/acceptance_*.md` (groups AC-H, AC-O, AC-P, router/filter AC-R8–R12, plus additions to E/S/G). New code should move toward these decisions, not away from them:
- **Parser and site theme**: the site uses an `irs-*` theme. Main content is `div.irs-blog-single-col` or `section.irs-blog-single-field div.col-md-8`, and the sidebar is `irs-side-bar`. The old index was built before the parser matched this theme, so it contains whole pages with sidebar images, video and view counters, which explains the image/video duplication. The parser now also strips `irs-info-text` (date and view counter) after reading the date. Parser changes must come with real-HTML fixtures (`tests/fixtures/`, `test_parser_theme.py`). Incremental now uses the same rules (`indexer.index_page`).
- Media is moving to `media` (unique by sha256) + `media_occurrence`, with video keyed by YouTube id. OCR state becomes explicit columns (`ocr_status`) instead of parsing `sub:`/`ocr:` markers in captions.
- **Qdrant stays the vector store** (D8; pgvector was considered and rejected). Postgres holds metadata and relations only. Consistency between them relies on deterministic uuid5 point ids from `compute.py` artifacts, so upserts overwrite instead of duplicating, plus a nightly reconcile. Accent-insensitive keyword search uses sparse BM25 on folded tokens (replaces the earlier `text_folded` + full-text-index draft, which only filters and cannot rank). Cutover is blue/green via the `*_v2` collections (config default); rollback = point the API's `QDRANT_COLLECTION_TEXT/IMAGE` back to `sict_text`/`sict_image`. Schema changes still go through `db.init_db` ALTERs; Alembic is deliberately deferred until a breaking (rename/drop) schema change, since v2 only adds tables/columns.
- Embeddings are moving to **ONNX Runtime int8** with no torch in either image. The CLIP text side becomes `clip-ViT-B-32-multilingual-v1`, which shares the CLIP B/32 image space, so image vectors stay valid. Keep the `embedder` function signatures stable.
- Schema changes go through Alembic from stage 3 on (not `db.init_db` ALTERs).
- Hardware (D32): VM1 c7i-flex.large (2 vCPU / 4 GB: stores + API + nginx), VM2 its own EC2 with 2 vCPU / 8 GB (embed service + `cron` worker + Obscura; the worker stays there instead of serverless, see D32). VM1 limits (2026-11-01, total 3,650 MB): postgres 600, redis 300, qdrant 1,100 (peak 786), api 1,500 (index v2 loads E5 + CLIP in the API; `API_MEM_LIMIT=600m` after the v3 cutover, measured ~200 MiB with `EMBED_BACKEND=api`), nginx 150. Keep the sum of `mem_limit` per VM within physical RAM. API runs one uvicorn worker (each worker reloads the models).
